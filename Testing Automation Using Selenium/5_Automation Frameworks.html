5.1

What is an Automation Framework?

An automation framework is a structured way of organizing everything a test suite depends on — so that adding test #200 is exactly as manageable as adding test #2.

Test scripts

The actual @Test methods that drive assertions.

Test data

Inputs kept separate from logic so scripts don't hard-code values.

Configuration

Environment URLs, browser choice, timeouts — kept out of test logic.

Page objects

One class per screen, isolating locators from test logic.

Utilities

Shared helpers — readers, waits, formatters — reused across tests.

Reports

Pass/fail output stakeholders can actually read after a run.

Test execution

How and in what order suites actually run.

Logging

A trail of what actually happened, for when a test fails at 2am.

Without a framework

This is where most beginner projects start — and where they stop scaling.

Test1.java Test2.java Test3.java Test4.java
No shared structure, no reusable page logic, no separation between data and code. Every new test duplicates setup and teardown by hand — and every small UI change means editing locators in four different places instead of one.

5.3

TestNG

TestNG is the test framework that lets us organize and execute tests — grouping them, ordering them, and controlling what happens before and after each one runs.

LoginTest.java 
import org.testng.annotations.Test;

public class LoginTest {

    @Test
    public void validLoginTest() {

        System.out.println("Executing login test");

    }
}

TestNG Lifecycle

Every TestNG run follows a fixed order of annotations — this is what lets setup and cleanup happen automatically around every single test.

@BeforeSuite
@BeforeTest
@BeforeClass
@BeforeMethod
@Test
@AfterMethod
@AfterClass
@AfterTest
@AfterSuite
TestNGDemo.java 
import org.testng.annotations.*;

public class TestNGDemo {

    @BeforeMethod
    public void setup() {
        System.out.println("Browser setup");
    }

    @Test
    public void loginTest() {
        System.out.println("Login test");
    }

    @AfterMethod
    public void tearDown() {
        System.out.println("Browser closed");
    }
}
5.5

BaseTest

BaseTest centralizes the setup and teardown every test needs, so individual test classes only contain test logic — not repeated browser boilerplate.

BaseTest.java 
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeDriver;
import org.testng.annotations.AfterMethod;
import org.testng.annotations.BeforeMethod;

public class BaseTest {

    protected WebDriver driver;

    @BeforeMethod
    public void setup() {

        driver = new ChromeDriver();

        driver.manage().window().maximize();

    }

    @AfterMethod
    public void tearDown() {

        if (driver != null) {
            driver.quit();
        }
    }
}

Why this matters at scale

Every test class that extends BaseTest inherits this setup and teardown for free — a fresh, maximized browser before each @Test method, and a guaranteed quit() afterward, even if the earlier tests in a class failed. That reliability is exactly what a hand-written Test1.java / Test2.java pile from 5.1 doesn't give you.
