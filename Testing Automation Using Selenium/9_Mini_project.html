OBJECTIVES

What this project measures

By the end, a student should be able to design a test automation framework that a QA team could actually extend and maintain — not just a script that happens to pass once.

1Structure a Maven-based automation project following industry folder conventions.
2Implement the Page Object Model to separate locators from test logic.
3Automate both positive and negative end-to-end flows.
4Synchronize tests correctly using explicit waits, not fixed sleeps.
5Externalize configuration and test data instead of hard-coding values.
6Produce a reusable, independently-runnable suite with clear reporting.
SCENARIO

Brief

Your role: SDET / QA Automation Engineer

You've joined the QA team of an e-commerce company. Manual regression testing before every release is slowing the team down, and the product keeps shipping with issues that should have been caught earlier.

Your job is to build an automation framework that covers the application's core customer journey — launch, login, search, product details, and cart — reliably enough that it can run unattended in CI.

EMPHASIZE THROUGHOUT

Industry best practices

These are what separate a maintainable automation framework from a pile of Selenium scripts that happen to work today.

1

Don't automate everything

Automation is a business decision — weigh ROI, not just feasibility.

2

Avoid hard waits

Fixed sleeps make suites slow and still flaky.

Avoid
Thread.sleep(5000);
Prefer
new WebDriverWait(driver, ...)
3

Use Page Object Model

Don't duplicate locators across test files — one page, one source of truth.

4

Use meaningful names

Bad
test1()
Better
verifyValidUserCanLogin()
5

Keep test data separate

Don't hard-code values — read them from testdata/ or config.properties.

6

Use version control

Git → GitHub, with meaningful commits — same discipline as production code.

7

Make tests independent

One test should ideally not depend on another test's execution order.

8

Build stable selectors

Prefer stable attributes the application team provides:

locator.java
By.cssSelector("[data-testid='login-button']")
9

Don't overuse XPath

Overused
//div[3]/span[contains(...)]
Prefer
By.id("login-btn")
10

Handle synchronization properly

Understand the difference and teach why it matters, not just the syntax:

Implicit Wait Explicit Wait Fluent Wait
11

Reports matter

A professional suite communicates far more than a pass/fail count:

PASS FAIL SKIPPED Execution Time Failure Details Screenshots Logs
12

Automation code is software

Treat it like production code — every item on this list applies to the automation repo, not just the application it tests:

Clean code Code review Version control Reusable components Configuration management Documentation CI/CD Maintenance
WHAT TO SUBMIT

Deliverables

A complete Maven project matching the expected folder structure, pushed to a GitHub repository.
All six test cases automated and runnable in one go via testng.xml.
A generated execution report showing pass/fail status, execution time, and failure screenshots.
A README.md explaining the framework's structure and how to run the suite locally.

Final word

This isn't graded on whether six tests happen to pass once — it's graded on whether another engineer could clone the repo, read the README, and run the suite without asking you a single question.

That's the actual difference between a Selenium script and an automation framework.
