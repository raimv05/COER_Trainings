Page Object Model + Data-Driven Testing

Two ideas that turn a pile of working scripts into a framework a team can actually maintain: keep every locator in exactly one place, and stop hard-coding the same test logic once per data value.

7.1

Why Page Object Model?

Imagine 50 tests each contain their own copy of By.id("username"). Then the application changes: the field is renamed from username to userEmail.

✕ Without POM
LoginTest1.java → By.id("username") LoginTest2.java → By.id("username") LoginTest3.java → By.id("username") …and 47 more files, each with the same locator hard-coded
The rename means opening and editing all 50 files, one by one.
✓ With Page Object Model

All 50 tests call loginPage.enterUsername(). None of them know or care what the underlying locator is — that knowledge lives in exactly one place:

LoginPage.java

The rename means editing one line, in one file.

The rename, either way

− By.id("username")
+ By.id("userEmail")
7.2

LoginPage

A page object: one class per screen, holding its locators privately and exposing only the actions a test actually needs.

LoginPage.java 
import org.openqa.selenium.By;
import org.openqa.selenium.WebDriver;

public class LoginPage {

    private WebDriver driver;

    private By username =
            By.id("username");

    private By password =
            By.id("password");

    private By loginButton =
            By.id("login");

    public LoginPage(WebDriver driver) {

        this.driver = driver;
    }

    public void enterUsername(String value) {

        driver.findElement(username)
              .sendKeys(value);
    }

    public void enterPassword(String value) {

        driver.findElement(password)
              .sendKeys(value);
    }

    public void clickLogin() {

        driver.findElement(loginButton)
              .click();
    }

    public void login(
            String username,
            String password) {

        enterUsername(username);
        enterPassword(password);
        clickLogin();
    }
}
7.3

Login Test

With the page object built, the test itself reads almost like plain English — extending BaseTest from Hour 5 for its setup and teardown.

LoginTest.java 
import org.testng.annotations.Test;

public class LoginTest extends BaseTest {

    @Test
    public void validLogin() {

        driver.get("https://example.com/login");

        LoginPage loginPage =
                new LoginPage(driver);

        loginPage.login(
                "student@example.com",
                "Password123"
        );

        System.out.println(
                "Login executed successfully"
        );
    }
}

7.5

Data-Driven Testing

Page objects solve locator duplication. Data-driven testing solves the next duplication problem: the same test logic, copy-pasted once per data value.

✕ Instead of this
Repeated.java 
login("user1", "pass1");
login("user2", "pass2");
login("user3", "pass3");
Adding a fourth user means writing a fourth near-identical line — and a fourth place to fix bugs.
✓ We use test data

One test method, driven by a @DataProvider. The logic is written once; only the data changes.

Adding a fourth user means adding one row to the data array — zero new logic.

TestNG DataProvider

LoginDataTest.java 
import org.testng.annotations.DataProvider;
import org.testng.annotations.Test;

public class LoginDataTest {

    @DataProvider(name = "loginData")
    public Object[][] loginData() {

        return new Object[][] {

                {"user1", "password1"},
                {"user2", "password2"},
                {"user3", "password3"}

        };
    }

    @Test(dataProvider = "loginData")
    public void loginTest(
            String username,
            String password) {

        System.out.println(
                "Testing: "
                + username
                + " / "
                + password
        );
    }
}
