2.2 REQUEST ORDERING

Lower timestamp always wins

P1 → REQUEST(5)
P2 → REQUEST(7)
P3 → REQUEST(6)

Because 5 < 6 < 7, the service order is:

P1
→
P3
→
P2
TIE-BREAKER

If timestamps are equal, process IDs are used as a tie-breaker. For example:

(5, P1)
(5, P2)

then (5, P1) < (5, P2) — P1 goes first.

2.3 JAVA REQUEST QUEUE

Encoding the ordering rule in Java

Request.java 
import java.util.PriorityQueue;

class Request implements Comparable<Request> {

    int timestamp;
    int processId;

    Request(int timestamp, int processId) {
        this.timestamp = timestamp;
        this.processId = processId;
    }

    @Override
    public int compareTo(Request other) {

        if (this.timestamp != other.timestamp) {
            return Integer.compare(
                    this.timestamp, other.timestamp);
        }

        return Integer.compare(
                this.processId, other.processId);
    }

    @Override
    public String toString() {
        return "(" + timestamp + ", P" + processId + ")";
    }
}

This provides an excellent bridge from logical clocks (the previous module) to distributed mutual exclusion — the comparator is just the happened-before tie-breaking rule, encoded directly.

2.5 PRIORITY RULE

Whoever asked first, wins

CASE 1
P1 = 10
P2 = 15

P1 has priority.

CASE 2 (REVERSED)
P2 = 10
P1 = 15

P2 gets priority.

It's always about the timestamp, never about identity — whichever process genuinely asked first (lower logical timestamp) gets to go first. This is the exact same ordering rule from 2.2, just applied without the separate RELEASE message.

2.6 BEGINNER-FRIENDLY JAVA SIMULATION

A starting point to build on in class

RicartAgrawalaDemo.java 
class Process {

    private final int id;
    private int clock = 0;

    public Process(int id) { this.id = id; }

    public void requestCriticalSection() {
        clock++;
        System.out.println(
                "P" + id + " requests CS at clock " + clock);
    }

    public int getClock() { return clock; }
    public int getId() { return id; }
}

public class RicartAgrawalaDemo {

    public static void main(String[] args) {

        Process p1 = new Process(1);
        Process p2 = new Process(2);
        Process p3 = new Process(3);

        p1.requestCriticalSection();
        p2.requestCriticalSection();
        p3.requestCriticalSection();

        System.out.println("\nPriority based on timestamp:");
    }
}
2.6 EXTENDING THE SIMULATION

What a full implementation needs to track

For classroom purposes, extend this in a second step by maintaining four pieces of state per process:

requestTimestamp

The logical clock value attached to this process's own pending request.

repliesReceived

A running count (or set) of which other processes have replied so far.

deferredReplies

Requests this process has deliberately held back a REPLY for, because its own request has priority.

requestingState

Whether this process is currently idle, requesting, or inside the critical section.

RECAP

Hour 14 — Key takeaways

📨 Lamport's: 3 messages

REQUEST, REPLY, and RELEASE, ordered strictly by (timestamp, processId).

🧮 Timestamps drive everything

Lower timestamp always wins; equal timestamps fall back to process ID as a tie-breaker.

🤝 Ricart–Agrawala: 2 messages

Just REQUEST and REPLY — no separate release, since a deferred reply does that job instead.

requestTimestamp, repliesReceived, deferredReplies, and requestingState turn the algorithm from theory into working code.
