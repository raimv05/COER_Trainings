6.2 PARTIAL FAILURE

One of the most important concepts in this course

Server A
Server B ✕
Server C ✓

Server B can fail while A and C continue running normally.

This is called a partial failure — and it's the defining difference between distributed systems and single-machine programs. In a local program, either everything works or the whole process crashes. In a distributed system, some parts can be up while others are down, and your code has to handle that in-between state gracefully.

6.4 NETWORK PARTITION

When the network splits the cluster

Node A
----
Node B
✕
Node C
----
Node D

A network failure separates the cluster into isolated groups — {A, B} can no longer reach {C, D}.

Both sides may still be alive and fully functional on their own — but they can't coordinate with each other. This creates major consistency and availability challenges: each side has to decide whether to keep serving requests without knowing what the other side is doing.

6.5 CAP PERSPECTIVE

You can't have it all during a partition

Under a network partition, a distributed data system cannot simultaneously guarantee both:

✅ Perfect Consistency

Every node returns the exact same, latest data.

🟢 Availability

Every request gets a response, even from an isolated node.

...while also tolerating that partition. You have to pick which one you sacrifice.

6.5 CAP PERSPECTIVE — WORKED EXAMPLE

Without coordination, replicas diverge

Node A
₹1000
Receives: Withdraw ₹500
✕ NETWORK
Node B
₹1000
Receives: Withdraw ₹700

Both nodes started identical and both processed a valid-looking withdrawal — but they can't tell each other about it.

Node A now thinks the balance is ₹500. Node B thinks it's ₹300. Neither is "wrong" from its own point of view — but the replicas have diverged, and someone will need to reconcile them once the network heals.

6.6 JAVA FAILURE SIMULATION

Never assume a service is always available

FailureDemo.java 
public class FailureDemo {

    public static void main(String[] args) {

        boolean serverAvailable = false;

        try {

            if (!serverAvailable) {
                throw new RuntimeException(
                        "Server is unavailable");
            }

            System.out.println("Request successful");

        } catch (RuntimeException e) {

            System.out.println(
                    "Request failed: " + e.getMessage());
        }

        System.out.println("Application continues...");
    }
}

A professional distributed application should never assume another service is always available — every network call needs a plan for what happens when the answer is "no."

6.6 RESILIENCE PATTERNS

How professional systems handle unavailability

⏱️ Timeout

Stop waiting after a fixed time instead of hanging forever on a slow or dead service.

🔁 Retry

Automatically try the request again — often with a growing delay between attempts.

🪂 Fallback

Return a default or cached response when the real service can't answer.

🚫 Circuit Breaker

Stop sending requests to a failing service temporarily, so it gets time to recover.

♻️ Idempotency

Design requests so repeating them (after a retry) never causes duplicate side effects.

RECAP

Hour 6 — Key takeaways

📡 Networks aren't reliable

Delay, loss, disconnection, duplication, and reordering are all normal — not edge cases.

⚠️ Partial failure is the norm

Some parts of the system can fail while others keep working — code must handle that in-between state.

🧭 CAP forces a choice

During a partition, you trade off consistency and availability — you can't have both perfectly.

🛡️ Design for failure

Timeout, retry, fallback, circuit breaker, and idempotency turn "the service is down" from a crash into a handled case.
