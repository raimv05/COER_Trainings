4.2 TWO-TIER ARCHITECTURE

Client talks directly to the database

Client
↓
Database

No server layer in between — the client connects straight to the database. Simple to build, but it doesn't hold up in production.

PROBLEMS
🔓 Security — clients need direct DB credentials
📉 Scalability — every client opens its own DB connection
🔗 Tight coupling — client is locked to the database's exact schema

4.5 PEER-TO-PEER

No permanent central server required

Every node can act as both a client and a server. Nodes connect directly to each other, sharing the workload instead of relying on one central point.

Real examples

4.6 MICROSERVICES ARCHITECTURE

One giant app → many small services

INSTEAD OF
One giant application

Every feature lives in the same codebase, deploys together, and scales together — even if only one part is under load.

WE HAVE

Payment Service
User Service

Each service can be independently deployed and scaled — if Payment Service gets slammed on sale day, only that service needs more instances.

Producers, brokers, and consumers

Kafka — the industry example

Kafka distributes topic partitions across brokers and uses partitions as the unit of parallelism. Ordering is guaranteed within a partition, not globally across all partitions — a subtlety that trips up a lot of engineers new to event-driven systems.

4.8 JAVA ARCHITECTURE SIMULATION

Simulating microservices in one file

MicroserviceDemo.java 
class UserService {

    public void createUser(String name) {
        System.out.println("Creating user: " + name);
    }
}

class OrderService {

    public void createOrder(int orderId) {
        System.out.println("Creating order: " + orderId);
    }
}

class PaymentService {

    public void processPayment(double amount) {
        System.out.println("Processing payment: ₹" + amount);
    }
}

public class MicroserviceDemo {

    public static void main(String[] args) {

        UserService userService = new UserService();
        OrderService orderService = new OrderService();
        PaymentService paymentService = new PaymentService();

        userService.createUser("Rahul");

        orderService.createOrder(101);

        paymentService.processPayment(1499);
    }
}
4.8 JAVA ARCHITECTURE SIMULATION

Reading it as separate services

3 classesUserService, OrderService, and PaymentService each own exactly one responsibility — the single-responsibility principle microservices are built on.
In productionThese wouldn't be Java classes in one file — each would be an independently deployed process or container, likely with its own database.
main()Here it's a simple sequential call chain, but in a real microservices system these calls would happen over the network — via REST, gRPC, or an event broker.

Hour 4 — Key takeaways

🏗️ Layers grow to solve problems

Client-server → two-tier → three-tier → multi-tier each add a layer to fix a specific weakness of the one before it.

🕸️ Peer-to-peer skips the server

Every node shares the load directly — powering BitTorrent and blockchain networks.

🧩 Microservices scale independently

Breaking a monolith into services means each can be deployed and scaled on its own.

📡 Events decouple systems

Producers and consumers never talk directly — a broker like Kafka sits in between, ordering guaranteed only within a partition.
