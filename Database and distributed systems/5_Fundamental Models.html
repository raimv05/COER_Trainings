Every distributed system — no matter the architecture — can be reasoned about through the same three lenses. Before we can talk about clocks, ordering, or failures later in this course, we need shared vocabulary for these three.

Interaction Model

MODEL 1 OF 3

Interaction Model — how processes communicate

1

Before you can design or debug a distributed system, you need to know the rules of how its parts talk to each other.

Key questions to always ask

  • How fast is communication?
  • Is communication synchronous?
  • Is communication asynchronous?
  • Can messages be delayed?
MODEL 2 OF 3

Failure Model — what can go wrong

2

A distributed system spans many machines and networks — which means there are many more places for things to break than in a single program.

Examples every engineer must plan for

  • Server crash
  • Network failure
  • Message loss
  • Timeout
  • Process failure
MODEL 3 OF 3

Security Model — what an attacker can do

3

Once processes are talking over a network, that network is also open to anyone with bad intentions — not just your trusted services.

Examples to defend against

  • Impersonation
  • Unauthorized access
  • Message interception
  • Malicious requests
5.1 SYNCHRONOUS VS ASYNCHRONOUS

Does the client wait, or move on?

SYNCHRONOUS
Client → Request
↓
WAIT
↓
Server → Response

The client blocks and does nothing else until the server replies.

ASYNCHRONOUS
Client → Message Queue
↓
Server

The client hands off the message and doesn't necessarily wait for a response.

5.2 JAVA THREAD SIMULATION

Simulating asynchronous servers with threads

AsyncDemo.java 
class Server implements Runnable {

    private String name;

    public Server(String name) {
        this.name = name;
    }

    @Override
    public void run() {

        System.out.println(name + " started.");

        try {
            Thread.sleep(2000);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }

        System.out.println(name + " completed.");
    }
}

public class AsyncDemo {

    public static void main(String[] args) {

        Thread server1 = new Thread(new Server("Server-1"));
        Thread server2 = new Thread(new Server("Server-2"));
        Thread server3 = new Thread(new Server("Server-3"));

        server1.start();
        server2.start();
        server3.start();

        System.out.println("Client continues...");
    }
}
5.2 JAVA THREAD SIMULATION

Why completion order isn't guaranteed

implements RunnableThe Server class defines a task — the code any thread should run — without being a thread itself.
Thread.sleep(2000)Simulates work taking time, like a real network call or database query.
.start() x3All three threads are launched almost simultaneously and run independently, each on its own schedule.
"Client continues..."This line often prints before any server finishes — the main thread doesn't wait for the others. That's the asynchronous behavior in action.
Key lessonThreads execute independently, so the completion order isn't something the programmer should assume — it can change on every run.

RECAP

Hour 5 — Key takeaways

🔄 Interaction Model

Defines how fast, how synchronous, and how reliably processes communicate.

💥 Failure Model

Crashes, network failures, message loss, timeouts, and process failures must all be assumed possible.

🔐 Security Model

Impersonation, unauthorized access, interception, and malicious requests are always in scope.

🧵 Sync vs Async

Synchronous calls block and wait; asynchronous calls hand off work and move on — threads make this concrete and unpredictable in order.
