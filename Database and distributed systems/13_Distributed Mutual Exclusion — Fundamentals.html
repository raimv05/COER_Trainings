3. WHAT IS A CRITICAL SECTION?

The part of the code that can't be shared

A critical section is the portion of a program where a shared resource is accessed or modified.

critical-section.java 
balance = balance - 500;

If multiple processes execute this simultaneously without coordination, incorrect results can occur — the exact lost-update problem from Hour 8, now across independent machines instead of threads.

6. REQUIREMENTS OF MUTUAL EXCLUSION

What makes an algorithm actually good

🛡️Safety
⏳Liveness
⚖️Fairness
🚫No deadlock
🩺Fault awareness

1. Safety

Never allow two processes into the critical section simultaneously.

P1 → CS
P2 → CS   ❌

2. Liveness

A requesting process should eventually get access — not be stuck forever.

3. Fairness

Requests should not be indefinitely ignored in favor of others.

4. No deadlock

Processes shouldn't wait forever because of the algorithm itself.

5. Fault awareness

The algorithm should consider process and network failures — a crashed process should never be able to permanently lock everyone else out.

7. MUTUAL EXCLUSION THEOREM / SAFETY CONDITION

The fundamental property, stated precisely

At any instant, at most one process may execute its critical section for a particular shared resource.

If the critical sections of two different processes ever overlap in time:

CS(Pi) ∩ CS(Pj) ≠ ∅

...the mutual exclusion property is violated.

For teaching purposes, the simplest way to remember it:

Processes in CS ≤ 1
8. CLASSIFICATION

Two major families of algorithms

Distributed Mutual Exclusion
Token-based
Non-token-based

🎫 Token-based

Possession of a token gives permission to enter the critical section — only one token exists, so only one process can hold it.

Token Ring Suzuki–Kasami

💬 Non-token-based

Processes communicate through request/reply messages and negotiate access directly with each other.

Lamport's algorithm Ricart–Agrawala
9. JAVA FOUNDATION — CRITICAL SECTION

Mutual exclusion inside a single JVM

SharedResource.java 
class SharedResource {

    private int value = 0;

    public synchronized void update(String processName) {

        System.out.println(
                processName + " entered critical section.");

        value++;

        try {
            Thread.sleep(1000);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }

        System.out.println(
                processName + " leaving critical section.");
    }
}

public class MutualExclusionDemo {

        Thread p1 = new Thread(

Hour 13 — Key takeaways

🔒 Mutual exclusion, everywhere

Any time a critical section touches shared state, only one participant can be inside it at a time.

🏛️ Centralized vs. distributed

A coordinator simplifies the decision but becomes a single point of failure — distributed systems often have no coordinator at all.

✅ Five requirements

Safety, liveness, fairness, no deadlock, and fault awareness define what "good" means for these algorithms.

🎫 Two families

Token-based (Token Ring, Suzuki–Kasami) and non-token-based (Lamport's, Ricart–Agrawala) — both studied in the hours ahead.
