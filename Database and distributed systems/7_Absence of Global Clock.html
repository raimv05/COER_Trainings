7.1 THE PROBLEM

Which event happened first?

Computer A
10:00:01
Computer B
10:00:03
Message

Computer A's clock says 10:00:01, Computer B's clock says 10:00:03 when the message arrives. It looks obvious — A happened first. But can we actually trust that?

We cannot blindly trust physical clocks. Two machines rarely show the exact same time, and that small gap is enough to make "which happened first" a genuinely hard question.

7.2 WHY?

Why physical clocks can't be trusted blindly

🐢Clock drift
🧭Different clock sources
📡Network delay
⚠️Synchronization errors

Even NTP synchronization — the standard protocol computers use to sync their clocks — doesn't make distributed systems behave as if they possess a perfectly synchronized global clock. There's always some residual error, and that error is enough to make simple timestamp comparisons unreliable.

7.3 REAL-LIFE EXAMPLE

Two ATMs, two timestamps

🏧 ATM A

10:00:01
Withdraw ₹500

🏧 ATM B

10:00:00
Withdraw ₹700

ATM A's clock says its withdrawal happened at 10:00:01. ATM B's clock says its withdrawal happened at 10:00:00 — a second earlier. Which one actually happened first?

Physical timestamps alone may not provide a reliable causal ordering. If ATM B's clock is running fast, its withdrawal might actually have happened after ATM A's — the timestamps are lying to us, and a bank auditing these transactions can't just trust the printed time.

7.4 EVENT ORDERING

Asking a better question

THE OLD QUESTION
"What exact time did this event happen?"
→
THE BETTER QUESTION
"Did event A happen before event B?"

Instead of relying on exact timestamps, distributed systems reason about the order of events relative to each other. This shift in thinking is what leads directly to logical clocks — the topic we'll build starting next hour.

7.5 JAVA PHYSICAL CLOCK DEMONSTRATION

What System.currentTimeMillis() actually gives you

PhysicalClockDemo.java 
public class PhysicalClockDemo {

    public static void main(String[] args) {

        long timeA = System.currentTimeMillis();

        performTaskA();

        long timeB = System.currentTimeMillis();

        System.out.println("Event A: " + timeA);
        System.out.println("Event B: " + timeB);
    }

    static void performTaskA() {

        try {
            Thread.sleep(100);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
7.5 JAVA PHYSICAL CLOCK DEMONSTRATION

Why this still isn't enough

timeACaptures this machine's clock reading right before the task runs — accurate for this machine only.
performTaskA()Simulates real work taking time, just like a network call or database write would.
timeBCaptures the clock again afterward — on the same machine, timeB will always be ≥ timeA. That's the one guarantee a physical clock gives you.
The catchThat guarantee breaks the moment a second machine is involved — its clock may run faster, slower, or simply be set differently.

Physical timestamps are useful, but distributed ordering requires a deeper abstraction — one that doesn't depend on every machine's clock agreeing. That abstraction is what we build next: logical clocks.

Hour 7 — Key takeaways

🕒 No shared clock exists

Every machine has its own clock — there's no single "true time" they all agree on.

⚠️ Drift, delay, and error compound

Clock drift, different sources, network delay, and sync errors all chip away at trust in physical timestamps — even with NTP.

🏧 Real systems feel this

Two ATMs with slightly different clocks can genuinely disagree on which transaction happened first.

🔀 Order matters more than time

Asking "did A happen before B?" instead of "what time did A happen?" is the doorway to logical clocks.
