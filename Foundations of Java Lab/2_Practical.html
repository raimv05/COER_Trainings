Employee Role & Payroll Management System

The HR team now needs to represent Developers, Testers, and Project Managers — each sharing common employee information but differing in responsibilities and salary logic. Built entirely in Core Java, this practical uses inheritance, abstraction, interfaces, and polymorphism to model that difference cleanly.

Part A — Employee.java
ENCAPSULATION

Create the Base Employee Class

Common employee information, kept private, exposed only through public accessor methods.

1
2
3
4
private String employeeId;
private String employeeName;
private String department;
private double basicSalary;

Expose them through paired accessors:

  • getEmployeeName() / setEmployeeName()
  • getDepartment() / setDepartment()
  • getBasicSalary() / setBasicSalary()
Industry practice — business data should generally not be exposed directly. Prefer employee.getBasicSalary() over reaching into employee.basicSalary — this is controlled access, the core of encapsulation.

Demonstrate Polymorphism

Different subclass objects, stored and invoked through the parent-class reference.

1
2
3

emp1.calculateSalary();

EXPECTED OUTPUT

What to notice — the reference type is Employee, but the actual object is Developer, Tester, or Manager — runtime polymorphism and dynamic binding in action.

Dynamic Method Dispatch — the JVM resolves which overridden method runs based on the actual object at runtime, not the reference type.

Part L — design-notes.md
COMPARISON

Procedural vs Object-Oriented Approach

A brief comparison of the two ways this system could have been structured.

Procedural

main() | +-- developer details +-- tester details +-- manager details +-- salary calculations +-- reports

Can become difficult to maintain as the application grows.

Object-Oriented

Employee | ------------------------- | | | Developer Tester Manager | Interfaces

Each object manages its own relevant behavior.

VIVA QUESTION

Why is OOP more suitable for a growing employee-management application?
