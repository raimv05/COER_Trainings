What is Inheritance?

Starting with a family of vehicles

🚙 Picture This Family

Every one of those three — Car, Bike, Truck — can start() and stop() the same way. But I don't want to write start() and stop() three separate times, once per class. Instead, I write them once on Vehicle, and let each specific type add only what makes it unique. Inheritance allows a class to derive from another class — that's the mechanism that makes this possible.

19

Basic Inheritance

Writing it for the first time

💻 Vehicle and Car

Vehicle.java
class Vehicle {

    void start() {
        System.out.println("Vehicle started");
    }

    void stop() {
        System.out.println("Vehicle stopped");
    }
}

class Car extends Vehicle {

    void drive() {
        System.out.println("Car is driving");
    }
}

Here's how I'd use it:

Main.java
public class Main {

    public static void main(String[] args) {

        Car car = new Car();

        car.start();
        car.drive();
        car.stop();
    }
}
Console Output Vehicle started
Car is driving
Vehicle stopped

I want you noticing this carefully: I never wrote start() or stop() inside Car — yet car.start() and car.stop() both worked. That's inheritance putting Vehicle's methods directly into Car's hands.

Inheritance Hierarchy

One parent, several children, each with its own extras

💻 Two Children, Two Different Extras

VehicleHierarchy.java
class Vehicle {

    void start() {
        System.out.println("Vehicle starts");
    }
}

class Car extends Vehicle {

    void openTrunk() {
        System.out.println("Trunk opened");
    }
}

class Bike extends Vehicle {

    void kickStart() {
        System.out.println("Bike kick-started");
    }
}

Both Car and Bike get start() for free from Vehicle, but only Car can openTrunk(), and only Bike can kickStart(). That's the whole point of a hierarchy — shared behavior at the top, specific behavior branching below it.

IS-A Relationship

The test I want you running before you ever write "extends"

🧪 Does It Actually Make Sense?

Before I let a class extend another, I ask myself whether a meaningful is-a relationship actually holds. These all pass my test:

Car IS-A Vehicle
Dog IS-A Animal
Manager IS-A Employee

But this one fails it:

Car IS-A Engine

A car isn't a kind of engine — a car has an engine. That's a completely different relationship, and I want you reaching for it instead:

Car HAS-A Engine → composition
💡
I want you treating this distinction as non-negotiable: this IS-A versus HAS-A distinction is extremely important in professional software design. Get it wrong, and you end up with class hierarchies that don't make sense and are painful to maintain.

super Keyword

Reaching back up to the parent's version of something

⬆️ What super Gives Me Access To

super refers to the immediate parent-class part of the object. Let me show you exactly what that means:

Manager.java
class Employee {

    String name = "Employee";

}

class Manager extends Employee {

    String name = "Manager";

    void displayNames() {

        System.out.println(name);
        System.out.println(super.name);

    }
}
Console Output Manager
Employee

Both classes have a field literally named name — plain name reaches the Manager version, and super.name reaches back to the Employee version underneath it. That's exactly what I mean by "the immediate parent-class part of the object."

Calling Parent Constructor

Letting the parent set up its own part first

🏗️ Building a Manager on Top of an Employee

Manager.java
class Employee {

    String name;

    Employee(String name) {

        this.name = name;

    }
}

class Manager extends Employee {

    String department;

    Manager(String name, String department) {

        super(name);

        this.department = department;
    }
}

I want this one line burned into memory:

The line in question
super(name);

This calls the parent constructor. I let Employee handle setting up name exactly the way it already knows how to, and Manager only takes responsibility for the piece that's new: department.

Method Overriding

Replacing the parent's behavior instead of just extending it

🔁 Giving a Dog Its Own Sound

Animal.java
class Animal {

    void makeSound() {

        System.out.println("Animal makes sound");
    }
}
Dog.java
class Dog extends Animal {

    @Override
    void makeSound() {

        System.out.println("Dog barks");
    }
}
Main.java
public class Main {

    public static void main(String[] args) {

        Dog dog = new Dog();

        dog.makeSound();
    }
}
Console OutputDog barks

Dog doesn't just inherit makeSound() as-is — it completely replaces it with its own version. That's overriding, and I want you clearly distinguishing it from overloading, which we'll get to separately.

Why @Override?

The one-line habit I want you building right now

🏷️ A Habit I'm Not Negotiable On

I want you using @Override every single time you override a method — no exceptions, starting today:

Annotation
@Override

Here's exactly what I'm telling the compiler when I write it: "I intend to override a superclass method." If my method signature is wrong — a typo in the name, a mismatched parameter type — the compiler catches it immediately instead of silently letting me create a brand-new, unrelated method by accident.

✅
This is a professional coding practice — not a beginner's training wheel you'll drop later. Every serious Java codebase you'll ever work in expects to see @Override on every overridden method.
