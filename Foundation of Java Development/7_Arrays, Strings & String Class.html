Arrays

Why I stop declaring a separate variable for every value

📚 The Problem With Separate Variables

Imagine storing four exam marks. My first instinct as a beginner might be this:

Before — Don't Do This
int mark1 = 80;
int mark2 = 75;
int mark3 = 90;
int mark4 = 85;

This falls apart immediately — what if there are 50 marks? 500? I'd need 500 separate variable names. Instead:

After — Use an Array
int[] marks = {80, 75, 90, 85};
80[0]
75[1]
90[2]
85[3]

One variable name, marks, holding four values side by side in memory — each accessed by its index, which always starts counting at 0.

✅
The rule I want you internalizing: reach for an array anytime you have multiple related values of the same type that you'll want to work with as a group — looping over them, searching them, sorting them.

Array Creation

Reserving space first, then filling it in

🧱 Creating a Fixed-Size Array

ArrayDemo.java
public class ArrayDemo {

    public static void main(String[] args) {

        int[] marks = new int[5];

        marks[0] = 80;
        marks[1] = 75;
        marks[2] = 90;
        marks[3] = 85;
        marks[4] = 70;

        System.out.println(marks[0]);

    }
}
Output80

Here's exactly what I want you tracing through step by step:

Step 1 — Reserve the space

new int[5] tells Java: "reserve five slots for integers, right now." Every slot starts at the default value 0.

Step 2 — Fill in each slot by index

marks[0] = 80; places 80 into the very first slot. Indexes run from 0 to 4 for a size-5 array — never 5 itself.

Step 3 — Read a value back out

marks[0] retrieves whatever is currently sitting in slot 0 — here, 80.

80[0]
75[1]
90[2]
85[3]
70[4]

The size you give new int[5] is fixed forever — you can change the values inside, but you can never grow or shrink this array after creation.

🚫
The error every beginner eventually hits: ArrayIndexOutOfBoundsException. For a 5-element array, valid indexes are 0 through 4 — trying to access marks[5] crashes the program immediately.

Loop Through Array

Visiting every element without repeating yourself

🔁 Classic for Loop

LoopDemo.java
int[] marks = {80, 75, 90, 85, 70};

for (int i = 0; i < marks.length; i++) {

    System.out.println(marks[i]);

}
Output80 75 90 85 70
i < marks.length ?
↓ true
print marks[i], then i++
↻ back to condition check
i == 5 → false → exit

marks.length gives you the array's size — 5 here — so the loop automatically stops right after the last valid index, 4.

✨ Enhanced for (the "for-each" loop)

EnhancedForDemo.java
for (int mark : marks) {

    System.out.println(mark);

}
Output80 75 90 85 70

Same result, no index variable at all — mark is automatically assigned each element in turn, from first to last.

💡
When I reach for each style: the classic for loop when I need the index itself (to modify elements, compare positions, or go backwards). The enhanced for when I just need to read each value in order — it's shorter and harder to get wrong.

Find Maximum

An excellent beginner exercise for combining loops and conditionals

🏆 Finding the Largest Number

MaxNumber.java
public class MaxNumber {

    public static void main(String[] args) {

        int[] numbers = {10, 45, 23, 89, 12};

        int max = numbers[0];

        for (int number : numbers) {

            if (number > max) {

                max = number;

            }

        }

        System.out.println("Maximum = " + max);

    }
}
OutputMaximum = 89

🔍 Tracing max Through Every Iteration

This is the exact trace I want you able to reproduce on a whiteboard for any interview:

numbernumber > max ?max after this step
start—10 (initial value)
1010 > 10 → false10
4545 > 10 → true45
2323 > 45 → false45
8989 > 45 → true89
1212 > 89 → false89

max only ever changes when the current element beats the best one seen so far — that's the entire algorithm.

✅
Why I always start with max = numbers[0], not 0: if every number in the array happened to be negative, starting from 0 would give the wrong answer. Starting from the array's own first element guarantees max begins as a value that's actually in the array.

for (int i = 0; i < matrix.length; i++) {

String Creation

Two ways to create a String — and which one I actually recommend

🏗️ Literal vs new

StringCreation.java
String firstName = "Rahul";

String lastName = new String("Sharma");

System.out.println(firstName);
System.out.println(lastName);
OutputRahul Sharma

String literal — "Rahul"

Java checks a special shared area called the String pool first. If an identical literal already exists there, it reuses it instead of creating a new object.

new String("Sharma")

Forces Java to create a brand-new object on the heap, every single time — even if an identical string already exists in the pool.

✅
For beginners, the rule is simple: string literals are generally preferred when appropriate. They're more memory-efficient because of pooling, and they're what you'll see in the vast majority of real code. Reach for new String(...) only when you have a specific reason to guarantee a distinct object.

String Immutability

A very important interview concept

❓ Why Doesn't This Work?

ImmutableDemo.java
String name = "Java";

name.concat(" Programming");

System.out.println(name);
OutputJava

Notice the output is still just "Java" — the concatenation appears to have done nothing at all. This trips up nearly every beginner the first time.

🔒 Why: Because String Is Immutable

String name = "Java"
↓ name.concat(" Programming") is called
a NEW String "Java Programming" is created in memory
↓ but nothing captured the result
the new String is discarded — name still points to the original "Java"

concat() never modifies the original String object — it can't, because String objects are immutable in Java. Every method that appears to "change" a string actually returns a brand-new one.

✅ The Correct Way

ImmutableFixed.java
name = name.concat(" Programming");

System.out.println(name);
OutputJava Programming

This time I'm capturing the new string that concat() returns and reassigning it back into name. name now points to the new object instead of the old one.

🚫
The rule I want burned in for interviews: every String method that looks like it modifies the string — concat(), replace(), toUpperCase(), substring(), all of them — actually returns a new String and leaves the original untouched. If you don't capture the return value, your change is silently lost.

== vs .equals()

Extremely important — and one of the most common Java bugs

⚔️ The Classic Gotcha

EqualsDemo.java
String a = new String("Java");
String b = new String("Java");

System.out.println(a == b);
System.out.println(a.equals(b));
Outputfalse true

🧠 Why Two Different Answers for the "Same" String?

a → new String("Java")
Heap Object #1
"Java"
b → new String("Java")
Heap Object #2
"Java"

Each new String(...) forces a distinct object on the heap — a and b point to two different boxes in memory, even though both boxes happen to hold the same text.

Operator / MethodWhat it actually checks
==reference identity for objects — are these two variables pointing at the exact same object in memory?
.equals()logical/content equality — do these two objects hold the same characters, regardless of where they live in memory?
🚫
The bug this causes in real code: using == to compare Strings can appear to work fine with literals (thanks to the String pool sharing objects) and then mysteriously break the moment a string comes from user input, a file, or a database — because those Strings are rarely pooled. Always use .equals() to compare String content. Reserve == for checking whether two references point to the literal same object.

Building Strings — StringBuilder

What to reach for when you're modifying text repeatedly

🧵 Why Not Just Keep Using String?

Because every String is immutable, repeatedly modifying one — say, inside a loop — creates a brand-new object every single time, which wastes memory and slows your program down. StringBuilder solves this: it's mutable, so it can grow and change in place.

StringBuilderDemo.java
public class StringBuilderDemo {

    public static void main(String[] args) {

        StringBuilder builder = new StringBuilder();

        builder.append("Java");
        builder.append(" ");
        builder.append("Programming");
        builder.append(" ");
        builder.append("Training");

        System.out.println(builder);

    }
}
OutputJava Programming Training

Unlike String.concat(), watch how the same object just keeps growing:

"Java"
→ append(" ")
"Java "
→ append("Programming")
"Java Programming"

No new object is created on each append() call — the same StringBuilder object is modified in place, which is exactly why it's far more efficient for repeated changes.

🛠️ The Core Methods to Know

append()

Adds text to the end.

insert()

Adds text at a specific position.

delete()

Removes a range of characters.

replace()

Swaps a range of characters for new text.

reverse()

Flips the entire sequence backwards.

toString()

Converts back into a regular immutable String.

StringBuilderChain.java
StringBuilder sb = new StringBuilder("Java");

sb.append(" Training");

sb.insert(0, "Core ");

System.out.println(sb);
OutputCore Java Training

Step 1 — Start

sb holds "Java".

Step 2 — append(" Training")

Adds to the end → "Java Training".

Step 3 — insert(0, "Core ")

Inserts at index 0, pushing everything else to the right → "Core Java Training".

✅
The decision rule I want you leaving with today: use a plain String when the text won't change. Reach for StringBuilder the moment you're building or modifying text repeatedly — especially inside a loop — since it avoids creating a new object on every single change.
