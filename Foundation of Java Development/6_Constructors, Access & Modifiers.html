What is a Constructor?

The special block that runs the moment an object is born

🏢 A Real-Life Analogy First

In a company

When a new employee joins, HR creates an employee profile and provides initial information — name, ID, department — before that employee does any actual work.

→

In Java

When an object is created, a constructor initializes the object — setting up its initial state before you ever call a method on it.

🧱 A Default Constructor

Student.java
class Student {

    String name;
    int age;

    Student() {

        name = "Unknown";
        age = 0;

    }

}

Creating the object:

Main.java
Student student = new Student();
new Student() is executed
↓ JVM allocates memory on the Heap
Student() constructor runs automatically
↓ sets name = "Unknown", age = 0
fully-initialized object handed to student

You never call Student() like a normal method — the new keyword triggers it automatically, exactly once, right when the object is created.

✅
The core idea I want you keeping: a constructor's job is to initialize an object. It shares its name with the class, has no return type at all — not even void — and Java calls it for you the instant you write new ClassName().

Parameterized Constructor

Initializing an object with real values right from the start

🎓 Creating a Student With Real Data

Student.java
class Student {

    String name;
    int age;

    Student(String name, int age) {

        this.name = name;
        this.age = age;

    }

    void display() {

        System.out.println(name);
        System.out.println(age);

    }
}

public class Main {

    public static void main(String[] args) {

        Student student = new Student("Rahul", 22);

        student.display();

    }
}
OutputRahul 22

🔍 Let's Break Down this.name = name;

This single line confuses almost every beginner the first time they see it, so let's dissect it fully:

this.name = name;
this.name LEFT SIDE — the object's own field (the box that stores data permanently on this object)
name RIGHT SIDE — the parameter that was just passed in (a temporary value, only alive during this call)

Left = object variable. Right = parameter. this exists specifically to tell Java "the field belonging to me, the object" — separating it from the parameter that happens to share the same name.

💡
Why not just name the parameter something else, like n? You could — but industry convention is to reuse the same name as the field for clarity, and then use this to disambiguate. Get comfortable reading this.field = parameter; — you'll see it constantly.

Constructor Overloading

Multiple ways to create the same kind of object

👤 Three Ways to Create an Employee

Employee.java
class Employee {

    String name;
    int salary;

    Employee() {

        name = "Unknown";
        salary = 0;

    }

    Employee(String name) {

        this.name = name;
        salary = 0;

    }

    Employee(String name, int salary) {

        this.name = name;
        this.salary = salary;

    }

}
CallWhich constructor runsResult
new Employee()no-argument constructorname = "Unknown", salary = 0
new Employee("Asha")single-String constructorname = "Asha", salary = 0
new Employee("Asha", 50000)String + int constructorname = "Asha", salary = 50000
✅
This is the exact same idea as method overloading from last hour: same name — here it's the class name, Employee — but different parameter lists. Java picks the right constructor based on what you pass to new Employee(...).

Constructor vs Method

Two things that look similar but do fundamentally different jobs

🆚 The Comparison I Want You to Know Cold

ConstructorMethod
Initializes objectPerforms operation
Same name as classCan have any valid name
No return typeHas return type or void
Called during object creationCalled explicitly
Cannot be inheritedMethods can be inherited
💡
The line I use to keep this straight: a constructor builds the object; a method makes an already-built object do something. You call a method whenever you want, as many times as you want — but a class's own constructor only runs once, automatically, at the exact moment new creates that object.

Access Specifiers

Controlling exactly who can see and use your code

🏬 Think About an Office Building

This is the analogy I want stuck in your head every time you choose an access specifier:

🚪
public
everyone can enter — the front lobby, open to all
🪪
protected
a specific group — this team and related teams (subclasses)
🏢
default
same department/package — no keyword needed, just leave it blank
🔒
private
only me — my own personal office, nobody else gets in

💻 All Four, on One Class

Employee.java
class Employee {

    public String name;

    private double salary;

    protected String department;

    int employeeId;

}

employeeId has no modifier at all — that absence of a keyword is the default access level: visible only within the same package.

🚫
A common beginner assumption I want you to drop: "no modifier" doesn't mean "no restriction" — it's not the same as public. Default access is genuinely more restrictive: it only opens the door to classes in the same package.

private + Getter/Setter

Protecting a field while still allowing controlled access to it

💰 An Industry-Relevant Example

Employee.java
class Employee {

    private double salary;

    public void setSalary(double salary) {

        if (salary >= 0) {

            this.salary = salary;

        }

    }

    public double getSalary() {

        return salary;

    }

}

🛡️ Why Go Through a Method At All?

private double salary
no direct outside access
→
setSalary(value)
validates: value >= 0 ?
→
salary safely updated
only ever valid values stored

Because salary is private, outside code can't write employee.salary = -500; directly. It has to go through setSalary(), which gets a chance to reject bad data before it's ever stored.

✅
This pattern has a name: encapsulation. Keep the field private so nothing outside the class can touch it directly, then expose controlled access through public getter and setter methods. The setter gives you a single, guaranteed choke point where you can validate every incoming value before it's stored.

Modifiers

Keywords that change how a member of a class behaves

🧰 The Ones You'll Encounter

static

Belongs to the class itself, shared across every object.

final

Value cannot be changed once assigned.

abstract

No implementation here — subclasses must provide it.

synchronized

Only one thread can run this at a time.

volatile

Always read the latest value across threads.

transient

Skip this field during serialization.

For this fundamentals session, I want you focused heavily on the first two: static and final. We'll cover the rest in depth later in the course.

🔢 static — Shared Across Every Object

Counter.java
class Counter {

    static int count = 0;

    Counter() {

        count++;

    }

}

Watch what happens across three separate objects:

new Counter() #1
count becomes 1
new Counter() #2
count becomes 2
new Counter() #3
count becomes 3
static int count — ONE shared copy

Every Counter object shares the exact same count variable — it doesn't belong to any single object, it belongs to the class itself. Each constructor call increments that one shared value.

🔒 final — Locked After Assignment

Config.java
final int MAX_USERS = 100;

Once MAX_USERS is assigned 100, it can never be reassigned — attempting to do so is a compile-time error, exactly like the PI constant back in Module 13.

🚫
Don't blur these two together. static and final solve completely different problems: static is about sharing — one copy across every object of the class. final is about immutability — a value that can never change once set. A field can even be both at once (static final), which is exactly how you'd declare a true class-wide constant.
