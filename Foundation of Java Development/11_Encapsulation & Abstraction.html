Encapsulation

Protecting data by controlling how it's reached

🏧 Think About an ATM

I want you picturing an ATM machine right now. You never directly manipulate what's actually sitting behind it:

🔒 What I never touch directly

  • Bank Database
  • Account Balance
  • Transaction Ledger

✅ What I interact through

  • Withdraw
  • Deposit
  • Check Balance

The machine hands me a small, controlled set of buttons, and everything behind those buttons — the actual data — stays protected. That's encapsulation, and I want that ATM picture in your head every time the word comes up.

11

Poor Design

What I want you to recognize as a red flag

⚠️ Here's the Mistake I Want You Avoiding

BankAccount.java (don't do this)
class BankAccount {

    public double balance;
}

The moment I mark balance as public, I've handed the keys to anyone holding a reference to this object. Watch what that lets them do:

account.balance = -500000;

I want you to feel how wrong that line looks. That's dangerous — nothing is stopping an account from going hundreds of thousands into the negative with a single careless assignment.

12

Encapsulation with private

Fixing the mistake I just showed you

🔐 Locking the Data Down

BankAccount.java
class BankAccount {

    private double balance;

    public void deposit(double amount) {

        if (amount > 0) {
            balance += amount;
        }
    }

    public double getBalance() {

        return balance;
    }
}

And here's how I'd use it:

Main.java
public class Main {

    public static void main(String[] args) {

        BankAccount account = new BankAccount();

        account.deposit(5000);

        System.out.println(
            "Balance: " + account.getBalance()
        );
    }
}
Console OutputBalance: 5000.0

Notice I can no longer write account.balance = -500000; at all — the compiler won't let me, since balance is private. The only door in is deposit(), and I put a guard (amount > 0) right at that door.

🧭 The Flow I Want You Tracing Every Time

private data
↓
controlled methods
↓
safe access

Lock the data down, expose only a controlled method, and what comes through that method is safe by design — not by accident.

13

Getter and Setter

The pattern you'll write constantly

🧱 A Practical Example

Employee.java
class Employee {

    private String name;
    private double salary;

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name;
    }

    public double getSalary() {
        return salary;
    }

    public void setSalary(double salary) {

        if (salary >= 0) {
            this.salary = salary;
        }
    }
}

I want you noticing the pattern I'm repeating: every private field gets a get method to read it safely, and a set method to write it — with a guard, where one makes sense. This is a practical, everyday example of encapsulation — you'll write this exact shape hundreds of times in your career.

Why Encapsulation Matters in Industry

The payoff that makes all of this worth it

🏭 Let Me Show You the Real Benefit

Say I have this field:

Employee.java
private double salary;

Later, a new business rule comes in. I can add this inside setSalary() without touching anything else:

Employee.java
if (salary < minimumSalary) {
    throw new IllegalArgumentException();
}

I didn't have to go hunt down every place in the codebase that touches an employee's salary — I changed it in exactly one place, because that one place was always the only legal entry point.

✅
This is the benefit I most want you walking away with: the internal implementation can change while the public contract remains stable. That's what makes large codebases survivable over years of change.
15

Abstraction

Hiding "how," exposing only "what"

Let me ask you something
When you drive a car, do you need to know exactly how fuel injection works?
No — and I want you to notice just how little you actually need to know to drive it well.

🚗 What You Actually Interact With

start()
accelerate()
brake()

That's the entire interface I need as a driver. The internal implementation is hidden. That's abstraction — and I want you distinguishing it clearly from encapsulation, which we'll do in a moment.

16

Abstraction with a Class

Writing the car's interface in code

🔧 One Public Method, Several Hidden Steps

Car.java
class Car {

    public void start() {

        checkFuel();
        startEngine();
        activateElectronics();

        System.out.println("Car started");
    }

    private void checkFuel() {

        System.out.println("Checking fuel...");
    }

    private void startEngine() {

        System.out.println("Starting engine...");
    }

    private void activateElectronics() {

        System.out.println("Activating electronics...");
    }
}

From the outside, all I ever call is:

Main.java
car.start();

I don't need to know about checkFuel(), startEngine(), or activateElectronics() at all — they're private, tucked behind the one method I'm allowed to call. The user doesn't need to know the internal steps, and that's exactly the point.

17

Encapsulation vs Abstraction

The distinction I test you on every single time

💡
I want you to take this section seriously — this distinction is very important for interviews, and it's one of the most commonly confused pairs in all of OOP.

⚖️ Side by Side

EncapsulationAbstraction
Controls access to data/implementationHides unnecessary implementation details
Often achieved with access modifiersAchieved using interfaces/abstract classes and good API design
Focuses on "how access is controlled"Focuses on "what should be exposed"
Example: private balanceExample: payment.pay()

The way I'd say it in one breath: encapsulation protects the data, abstraction simplifies the interface. They work together constantly, but they're answering two different questions.
