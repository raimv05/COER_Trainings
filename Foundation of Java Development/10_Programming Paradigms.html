Procedural Programming

The approach I want you to recognize first

🧮 Where My Focus Is Here

When I write procedural code, my focus is primarily on functions/procedures and the sequence of operations. Let me show you with a small banking program:

BankProgram.java
public class BankProgram {

    static double balance = 10000;

    static void deposit(double amount) {
        balance += amount;
    }

    static void withdraw(double amount) {
        balance -= amount;
    }

    public static void main(String[] args) {

        deposit(5000);
        withdraw(2000);

        System.out.println(balance);
    }
}
Console Output13000.0

Notice what I did: balance sits off on its own as shared data, and deposit() / withdraw() are just functions that reach out and operate on it. Everything here revolves around functions operating on data — that's the signature of procedural thinking, and I want you able to spot it on sight.

Object-Oriented Approach

Solving the same problem, differently

🏦 Modeling the Bank Account as an Object

Instead of keeping balance floating around separately, I'm going to fold it into an object along with the behavior that belongs to it:

BankAccount.java
class BankAccount {

    double balance;

    void deposit(double amount) {
        balance += amount;
    }

    void withdraw(double amount) {
        if (amount <= balance) {
            balance -= amount;
        }
    }
}

And here's how I'd use it:

Main.java
public class Main {

    public static void main(String[] args) {

        BankAccount account = new BankAccount();

        account.deposit(5000);
        account.withdraw(2000);

        System.out.println(account.balance);
    }
}
Console Output3000.0

(Here balance starts at the class default of 0.0 rather than the 10000 I hardcoded in the procedural version — I didn't initialize it, which is exactly the kind of detail I want you noticing.)

Instead of data and functions sitting apart, I've bundled them into one unit — the object. That bundling is the whole shift from procedural to OOP thinking.

Procedural vs OOP

Laying the two approaches side by side

⚖️ The Comparison I Want You to Internalize

ProceduralObject-Oriented
Focuses on functionsFocuses on objects
Data often separated from functionsData and behavior can be encapsulated
Good for smaller/simple problemsWell suited to complex domain models
Reuse mainly through functionsReuse through classes, composition, inheritance, interfaces
Data protection depends on designEncapsulation supports controlled access
Top-down approach is commonModeling around entities/responsibilities is common
🚫
Here's a claim I won't make, and I don't want you making it either: "OOP is always better than procedural programming." That's an oversimplification I'm deliberately steering you away from.
✅
What I actually want you carrying forward: different paradigms are useful for different problems. I reach for OOP specifically when the software needs to model complex entities, responsibilities, and relationships — not by default, by fit.

Four Pillars of OOP

The four ideas every OOP conversation eventually comes back to

This is the diagram I'd draw on the board — Encapsulation, Abstraction, and Inheritance branching off OOP directly, with Polymorphism building on top of Abstraction.

🧩 What Each One Actually Solves

I'll teach you these four as the "four pillars," since that's the name you'll hear everywhere — but I want you to understand them as solving four different problems, not as four versions of the same idea.

🔐

Encapsulation

Protect and control data.

🎭

Abstraction

Expose essential functionality while hiding unnecessary implementation details.

🧬

Inheritance

Create an "is-a" relationship and reuse/extend behavior.

🔁

Polymorphism

Allow a common interface/type to represent different implementations.
