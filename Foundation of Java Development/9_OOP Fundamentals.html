What is OOP?

The mindset shift I want you to make before we touch any syntax

Let me ask you something
If we were building Amazon, would we write the entire application as one huge sequence of instructions, top to bottom?
Obviously not. And I want you to understand exactly why not.

🧩 Instead, I'd Identify Entities

The first thing I'd do is look at the problem and pull out the real-world "things" involved:

⚙️ Every Entity I Identify Has Two Parts

Data
+

Let me show you with BankAccount — this is the pairing I want you internalizing for every entity you model from now on:

Data

  • accountNumber
  • holderName
  • balance

Behavior

  • deposit()
  • withdraw()
  • checkBalance()

This pairing — data plus behavior, bundled together — is the fundamental idea behind OOP. Everything else I teach you in this hour builds on that single idea.

16

Object

Turning "data + behavior" into something real

🧠 My Definition

An object is a runtime entity that contains state and behavior.

🚗 Let's Use a Car

🎨

State

color = red
brand = Toyota
speed = 80
+
🏎️

Behavior

start()
accelerate()
brake()
stop()

💻 Now Let's Write It in Java

Car.java
class Car {

    String brand;
    String color;
    int speed;

    void start() {
        System.out.println("Car started");
    }

    void accelerate() {
        speed += 10;
        System.out.println("Speed: " + speed);
    }

    void brake() {
        speed -= 10;
        System.out.println("Speed: " + speed);
    }
}

Notice what I did here: brand, color, and speed are the state, and start(), accelerate(), and brake() are the behavior — exactly the pairing I showed you above, now written as real code.

17

Class

Where that code actually comes from

📐 My Definition

A class is a blueprint / template from which objects can be created.

🏠 The Analogy I Want You Remembering Forever

📋

Class

House Blueprint
→
🏡

Object

Actual House

A blueprint tells you what rooms, doors, and dimensions a house should have — but you can't live in a blueprint. The same goes for a class: it describes what a Student should contain, but it isn't usable until you build one.

💻 Writing the Blueprint

Student.java
class Student {

    String name;
    int age;

    void study() {
        System.out.println(name + " is studying");
    }
}

This is the blueprint — it describes what every Student object should contain: a name, an age, and the ability to study(). I haven't built an actual student yet; that's next.

18

Creating an Object

Turning the blueprint into something I can actually use

🛠️ Let's Build a Student

Main.java
public class Main {

    public static void main(String[] args) {

        Student student = new Student();

        student.name = "Rahul";
        student.age = 21;

        System.out.println(student.name);
        System.out.println(student.age);

        student.study();
    }
}
Console Output Rahul
21
Rahul is studying

19

Multiple Objects

Why I only ever write the blueprint once

♻️ One Class, Many Objects

Here's something I want you to really appreciate: I only wrote the Student class once, but I can stamp out as many students from it as I need.

Main.java
public class Main {

    public static void main(String[] args) {

        Student student1 = new Student();
        student1.name = "Rahul";

        Student student2 = new Student();
        student2.name = "Priya";

        Student student3 = new Student();
        student3.name = "Amit";

        student1.study();
        student2.study();
        student3.study();
    }
}

class Student {

    String name;

    void study() {
        System.out.println(name + " is studying");
    }
}
Console Output Rahul is studying
Priya is studying
Amit is studying

This is exactly what I mean by reuse — one blueprint, three independent houses built from it.

One class, three independently-tracked objects — each with its own copy of name, and each sharing the same study() behavior.
